# 01. Архитектура

## Путь запроса

В локальном прототипе по теории браузер отправляет `POST /api/ask` серверу `web.py`. Сервер загружает ключ из `.env`/окружения, выполняет BM25 и запрос GigaChat через `rag.py` и `gigachat_client.py`, затем возвращает ответ и источники. При разработке Vite проксирует запросы к API. Готовую сборку React может раздавать Python-сервер с того же адреса, что и API. Ниже описан путь запроса целевой продуктовой версии.

1. Клиент открывает чат и восстанавливает выбранную раздачу. До первой раздачи текстовые вопросы передаются без идентификатора раздачи.
2. Сервер определяет вид сообщения с учётом вопроса и контекста. Для теории BM25 ищет правила, определения и стратегию. LLM объясняет понятие с примером, при необходимости используя открытую раздачу. После первого ответа чат получает понятное название.
3. Описание раздачи преобразуется в ту же структуру карт, позиций и ходов, что и ввод на столе. Исправление применяется к выбранной раздаче. При явно другой ситуации сервер предлагает создать отдельную раздачу и ждёт выбора пользователя.
4. При нехватке исходных данных сервер уточняет их и даёт общую префлоп-подсказку по известной руке. Если ситуация задана, код считает математику. Поиск возвращает фрагменты для объяснения и решение: точное или наиболее похожее по R-016. Код извлекает из решения действие и размер ставки.
5. LLM объясняет рекомендацию. Сервер сверяет действие и числа с результатами кода и сохраняет ответ с идентификаторами фрагментов. Клиент отображает ответ в контексте исходной раздачи, даже если пользователь успел открыть другую.
6. Фактический ход добавляется в историю. Код сравнивает ход пользователя с точным решением для состояния **до** хода по R-018 и обновляет стол по сделанному ходу. В разборе запрашивается пропущенный ход соперника и оценка показывается сразу. В тренировке ход соперника выбирается по его фиксированным картам из PokerBench, оценки раскрываются после завершения (R-019).
7. Клиент восстанавливает стол после каждого хода для пошагового просмотра, прокручивает ленту и показывает непрочитанные ответы по правилам REQ-010.

## Стек

| Часть | Выбор | Статус |
|---|---|---|
| Клиент | React, TypeScript, Vite, React Router, Redux Toolkit и `sessionStorage` | Чат по теории, ручной ввод параметров стола и демонстрационные раздачи |
| Сервер | Python 3.11+, стандартный `http.server`; FastAPI — предварительный вариант продуктового сервера | Локальный прототип сделан |
| Поиск | Собственный BM25; предобработка и benchmark — в [спецификации КТ по RAG](06-rag-checkpoint.md) | Сделано для теории |
| LLM | GigaChat v1 API, модель `GigaChat-3-Ultra`, OAuth и строгая JSON-схема | Сделано для прототипа теории |
| Хранилище | PostgreSQL для продуктовой версии (Q-003). Прототип по теории работает без БД | План |
| Решения солвера | CSV набора PokerBench в `data/pokerbench/`, чтение через `pandas` или модуль `csv` | Данные в репозитории, сборка фрагментов - план |
| Хостинг | Виртуальный хостинг REG.RU с Python/CGI и Passenger; GitHub Actions публикует `main` | Workflow подготовлен, первичная настройка доступа ожидается (D-017) |

Во фронтенде `pages/` и `components/` работают с Redux. `slices/trainerSlice.ts` управляет отправкой и состоянием запроса, `modules/trainerApi.ts` преобразует ответ в сообщение, а `api/` содержит HTTP-клиент и типы действующего `/api/ask`. Чат на TypeScript отправляет вопросы в RAG КТ2 и отображает ответ с источниками. `modules/sessionStorage.ts` сохраняет данные чатов и позицию ленты. Состояния ожидания и ошибки запроса существуют отдельно.

## Промпт

В рабочем прототипе 20B используется инструкция v2 о точном переносе фактов и полных ссылках. Конспекты D08/D30 дополнены воспроизводимыми уточнениями из `corpus/clarifications.json`. Нормализация сбрасывает/сбросил/сбросившего к фолду действует одинаково на запросы и документы.

После поиска `theory_answers.py` обрабатывает два узких типа вопросов при наличии подтверждающих источников. Код на Decimal считает слои банков по явно перечисленным взносам при пустом банке и олл-ине; возвращает состав банков до фолда и точный текст правила фолда из источника. В запросах о PokerBench код форматирует заданный префлоп-размер и считает минимальный повторный рейз после полного открытия при явно заданных блайндах. Возвращаются те же поля API и ссылки на найденные фрагменты, LLM в этих случаях не вызывается. Неоднозначные размеры, постфлоп, неуравнённая ставка одного игрока и непустой начальный банк остаются обычному RAG. Это не универсальный парсер раздач.

Для теории модель получает вопрос, фрагменты корпуса и при наличии контекст выбранной раздачи. Для рекомендации передаются фактическая ситуация, найденный пример, тип совпадения, действие, размер и расчёты. Модель возвращает объяснение и ссылки на фрагменты. Сравнение ходов и присвоение цветов выполняет код.

## Провайдер GigaChat (D-018)

По умолчанию используется GigaChat-3-Ultra: OAuth-токен получается сервером, кэшируется до истечения и обновляется; ответы запрашиваются со строгой JSON-схемой GigaChat v1. BM25, промпт и проверка ссылок сохраняются. Прежний клиент Groq доступен только при явном `LLM_PROVIDER=groq` для воспроизведения экспериментов.

## Локальное окружение Docker

Compose запускает Apache/Passenger с той же WSGI-точкой входа, отдельный MySQL 8.0.46 локально (на хостинге Percona 8.0.25-15) и опциональный Vite для разработки. Python 3.14.6 собирается на AlmaLinux 8.10; приложение и БД работают нативно на amd64 или arm64, без эмуляции. Docker используется локально, доставка файлов на REG.RU сохраняется. MySQL ещё не используется приложением. Конфигурация и ограничения совпадения описаны в Tech/02.

## Общие вопросы новичка

BM25 распознаёт ограниченный набор полных формулировок общего вопроса о покере/холдеме. При наличии D01/D02/D05/D06/D11 используется вводный подбор в этом порядке; оценки BM25 вычисляются по расширенному запросу о картах, блайндах, торговле и старшинстве. Ограничение k сохраняется. Другие вопросы и неполный вводный корпус используют прежний BM25. Промпт и проверка источников не меняются.

В профиле dev сервис reloader следит за Python-исходниками и обновляет общий с app маркер /app/tmp/restart.txt. Passenger перечитывает код на следующем запросе; Docker socket не используется. Обычный запуск не включает наблюдатель.

## Контекст и стиль диалога

Общий модуль conversation.py валидирует историю и разрешённые настройки оформления. Полные поддержанные просьбы о стиле обрабатываются кодом; произвольные инструкции не превращаются в системный промпт. Короткий буквальный префикс добавляет код, а краткость/подробность и простоту языка модель получает как ограниченные параметры. Для уточняющих формулировок поиск расширяется последними тематическими вопросами пользователя; новая самостоятельная тема ищется самостоятельно. Модель видит историю как сообщения user/assistant ниже системной инструкции, фактическая опора — только текущие документы. Точные расчётные ответы и проверка ID источников сохраняются.

Простое уточнение «А чем он отличается от колла?» после «Что такое чек?» преобразуется в явный вопрос о чеке перед поиском/генерацией. При явном упоминании Омахи/разза/стада без упоминания этой игры в найденных документах возвращается отказ до вызова модели. Это не является полной смысловой верификацией ответа. GigaChat получает до 1024 токенов вывода.
