# 05. Тесты и проверки

Результаты всех проверок записываются в `docs/Service/verification.md`.

## Фронтенд на TypeScript

Собрать `npm run build` в `code/client`. Запустить клиент через Vite и открыть готовую сборку через Python. Проверить, что чат, стили и шрифт загружаются, а демонстрационные формы входа и регистрации открываются. На `/frontend.html` открыть новый чат и проверить, что он появляется в боковой панели только после отправки первого сообщения. Проверить ручной ввод на столе и перезагрузить вкладку. Проверить, что сохранились активный чат и сообщение. Прокрутить ленту к середине и обновить вкладку. Проверить, что остались открыты тот же чат и та же часть ленты. При повторном выборе чата лента должна открыться в конце. Переключить раздачу и ход в демонстрационном чате, затем проверить независимое раскрытие переписки и «К столу». Свернуть выбранную раздачу и нажать «К раздаче». Карточка должна раскрыться, а лента прокрутиться к её концу. Нажать «Покинуть раздачу» и проверить, что лента остаётся на месте, а стол показывает пустые слоты и форму без «Решить». Проверить, что при редактировании кнопка «Решить» не появляется, а банк, ББ и анте редактируются в трёх отдельных полях. На первой демонстрационной раздаче проверить две точки действий игрока и возможность пройти ходы соперника стрелками.

Проверить ручной ввод общих карт. Тёрн доступен после заполнения флопа, ривер после тёрна. Одинаковая карта недоступна для повторного выбора, в том числе между картами игрока и бордом. Если заняты все четыре масти ранга, ранг недоступен. Позиция одного игрока недоступна другому.

Проверить отправку из чата через прокси Vite в `/api/ask` и раскрытие источников в ответе. Во время HTTP-запроса переключить чат и проверить, что ответ приходит в исходную переписку. Ответ с ошибкой должен завершить ожидание и сохранить вопрос в чате.

## Автотесты (`code/tests/`)

Реализованы тесты BM25, контракта ответа RAG, конфигурации Groq, локального HTTP API и Passenger WSGI-приложения. Таблица ниже описывает проверки целевой продуктовой версии, включая ещё не реализованные модули.

| Модуль | Что проверяем | Требования |
|---|---|---|
| Математика | Шансы банка и ауты на наборах известных примеров | REQ-008, R-004 |
| Вид вопроса | Теория и раздача определяются правильно на контрольных примерах | REQ-018, R-014 |
| Разбор ситуации | Поля из текста вопроса; неполный вопрос о раздаче даёт `clarify` | REQ-011, R-007 |
| Поиск | На контрольных запросах нужный фрагмент в top-5 | REQ-007 |
| Выбор действия | Точное решение имеет приоритет. При другой доске или стеке используется ближайшее решение. Аналог даёт совет и серую оценку хода без эталона | REQ-006, REQ-019, R-015 ... R-017 |
| API | Регистрация, вход, доступ только к своим раздачам, `401` без входа | REQ-001 ... REQ-003, R-011 |
| Ответ | Действие из словаря, числа совпадают с расчётами, статусы `no_sources` и `error` | REQ-006, REQ-012, REQ-013 |

Дополнительные проверки первой версии:

- Открыть новый чат, задать вопрос по теории, проверить название и скрытый стол. Создать две раздачи, переключиться, задать вопрос по первой и проверить обе переписки и их счётчики отдельно.
- Ввести одну ситуацию текстом и вручную, сравнить нормализованные данные и результат. Исправить карту и проверить, что обновилась выбранная раздача.
- Пройти GWT-018–020 и GWT-038–039: проверить оба направления навигации, прокрутку при печати и переход к новой раздаче, продолжение с фактического хода, фактический ход соперника в разборе, все четыре цвета и границу ровно 20%.
- Проверить переименование, удаление чата, восстановление последней раздачи, подсветку и определение термина, подпись об ИИ.

- Пройти GWT-041–042: проверить определение режима из текста, случайную раздачу, сохранение карт соперника, отсутствие подсказок и раскрытие оценок по завершении.

Запуск:

```bash
python -X utf8 -m unittest discover -s code/tests -v
```

Тесты не требуют ключа Groq. Отдельно они проверяют адрес и модель по умолчанию, а также чтение ключа из `GROQ_API_KEY`. `test_wsgi.py` проверяет Passenger WSGI-вход: health, передачу вопроса, старый маршрут `/ask`, безопасную раздачу сборки и ответы на неверные запросы.

HTTP-тесты поднимают сервер на свободном локальном порту с тестовым RAG: проверяют фронт, health, передачу вопроса и источников, валидацию, ошибку LLM, недоступность `.env` и загрузку настроек без выполнения shell-команд.

## CI и публикация

Файл `.github/workflows/deploy-regru.yml` запускается на Pull Request в `main` и на push в `main`. Job проверки запускает весь `unittest`, собирает фронтенд командой `npm ci && npm run build` и формирует пакет. Только успешный push в `main` запускает job деплоя в GitHub Environment `production`. Она передаёт пакет в document root через SSH+rsync, сохраняет `.env` и служебные каталоги, создаёт `.restart-app` и проверяет `DEPLOY_URL/api/health`. Проверка GitHub Actions не подтверждает доступность Groq или настройки конкретного хостинга; эти пункты проверяются после первого деплоя вручную.

Эксперимент промпта: сравниваются сохранённый исходный прогон и v2 на тех же вопросах и упорядоченных фрагментах `context`. Модель, temperature=0, reasoning_effort=low, JSON Schema и критерий оценки фиксируются. Изменяется только системная инструкция; эталоны не передаются модели. Прогон последовательный с паузами и ограниченными повторами API-ошибок. Инструкция v2 сейчас используется в `rag.py`. Сравнение на 15 известных вопросах — настройка, а не независимый тест обобщения; исторический baseline не контролирует изменения провайдера между прогонами.

Сравнение моделей: новые прогоны `openai/gpt-oss-20b` и `openai/gpt-oss-120b` с одним промптом-кандидатом v2 и теми же сохранёнными `context`. Изменяется только ID модели; temperature=0, reasoning_effort=low, max_tokens=700 и JSON Schema одинаковы. Ошибки попыток учитываются отдельно, критерий правильности прежний. Рабочая модель не переключается автоматически по результатам эксперимента.

Исправление Q04/Q05 на 20B: нормализация словоформ фолда, уточнённая инструкция о точном переносе машинного синтаксиса и различении взноса/выплаты. Приёмка — GWT-043/044, полный benchmark и дополнительные перефразировки с другими размерами ставок и взносами. Числовые расчёты не поручаются модели; если исходных сведений нет, применяется отказ.

[Спецификация и контрольные вопросы](06-rag-checkpoint.md) фиксируют корпус из 30 документов, 10 обычных вопросов, 5 ловушек и четыре метрики. Ниже описан расширенный продуктовый benchmark.

## Benchmark продукта (план)

Три части:
- **теория** - `code/tests/benchmark/theory.jsonl`, цель первой версии - 40-60 вопросов: термины, правила (порядок ходов, улицы, старшинство комбинаций), понятия стратегии;
- **раздачи** - `code/tests/benchmark/hands.jsonl`, цель первой версии - 40-60 раздач на русском (в основном префлоп), эталон по `R-009`. Проверяет всю цепочку от текста вопроса;
- **тест PokerBench** - `data/pokerbench/*/*test_set*.csv`: 1 000 префлоп-ситуаций и 10 000 ситуаций после флопа в структурированном виде. Проверяет поиск решения и выбор действия. Действия в тесте сбалансированы, случайный выбор даёт около 0.25.

**Метрика вида вопроса:** точность определения "теория / раздача" на обеих частях.

**Метрики поиска (без LLM, обе части):**
- Recall@5 — средняя по вопросам доля документов из `relevant_fragments`, попавших в top-5;
- MRR - насколько высоко стоит первый нужный фрагмент.

**Метрики ответа на теорию (с LLM):**
- полнота - доля `key_facts`, которые есть в ответе;
- корректность источников - среди `fragment_ids` есть нужный.

**Метрики ответа на раздачу (с LLM):**
- точность действия - доля совпадений с `expected_action`;
- допустимость действия - доля ответов из `acceptable_actions`;
- корректность источников - доля ответов, где среди `fragment_ids` есть нужный;
- ошибки формата - доля ответов, которые не удалось разобрать.

**Метрики на тесте PokerBench (без LLM), как в статье:**
- точность действия - совпал вид действия (фолд, чек, колл, бет или рейз);
- точное совпадение - совпали и действие, и размер ставки.

Пороги - в `REQ-015`.

**Сравнения:**
1. без предобработки / с лемматизацией;
2. разные способы построения запроса;
3. разные размеры фрагментов;
4. ответ с RAG / без RAG (показывает, что поиск помогает);
5. разбор раздач: корпус только с текстами / корпус с решениями PokerBench.

Каждый прогон сохраняется в `code/tests/benchmark/results/<дата>-<описание>.json` (параметры, метрики, ответы), итог - строкой в `docs/Service/verification.md`.

## Переход на GigaChat

Автотесты проверяют получение и обновление токена, формат JSON Schema, отсутствие ключа в ошибках и чтение настроек сервером. Сквозной запрос выполняется отдельно с ключом GigaChat; прежние оценки Groq не являются оценкой Ultra.

## Docker

Перед приёмкой проверить `docker compose config --quiet`, сборку app, health, ответ с источниками, версии Python/Apache/Passenger и SQL-параметры db по командам Tech/02. Выполнить автотесты в контейнере; проверить сохранение БД после пересоздания и прокси Vite в профиле dev. Не считать совпадение версий подтверждением полного совпадения конфигурации REG.RU.

## Общие вопросы по правилам

GWT-047/048: проверить вводные формулировки, варианты регистра и пунктуации, неизменность выдачи для терминов, других игр и смешанных вопросов, fallback при неполном корпусе. Проверить сквозной ответ GigaChat с источниками. После изменения поиска прогнать search-only benchmark КТ2 и сравнить метрики с текущим main.

В профиле dev проверить изменение, добавление и удаление Python-файла и маркер Passenger tmp/restart.txt; на HTTP-запросе новый код должен работать без пересоздания контейнера app. Без dev сервис reloader не запускается. Изменение .env требует force-recreate app.

GWT-049: проверить попадание GL25 в поиск для русского и английского написания постфлопа, непустое происхождение/лицензию и сквозной ответ с тремя улицами и ссылкой GL25. Search-only benchmark КТ2 выполняется отдельно от дополнительного корпуса.
