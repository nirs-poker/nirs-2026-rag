# 04. API и доступ

## API прототипа по теории

Для однозначно распознанных вопросов о банках и формате PokerBench ответ может формироваться кодом по найденным источникам без LLM. Состав JSON не меняется; ключ и внутренний способ обработки клиенту не требуются. Неподдержанные формы остаются в RAG, поэтому правильность произвольного ответа не гарантируется наличием ссылки.

`python code/server/web.py` запускает локальный посредник на `127.0.0.1:8001`. На виртуальном хостинге REG.RU с включёнными Python/CGI и Passenger точка входа `passenger_wsgi.py` вызывает WSGI-приложение из `code/server/wsgi.py` и обслуживает готовую сборку React из `code/client/dist/`. Оба режима используют один RAG и одинаковый контракт. Ключ авторизации GigaChat загружается на сервере из окружения или корневого `.env` и не возвращается клиенту. В режиме разработки чат вызывает локальный API через прокси Vite.

- `GET /api/health` → `200 {"status":"ok"}`: сервер доступен, без вызова GigaChat.
- `POST /api/ask` с `Content-Type: application/json` и телом `{"question":"Что такое кикер?"}` → результат RAG: `status`, `answer`, `sources`, `retrieved`. Вопрос — от 1 до 1500 символов.
- Ошибки: `400` — неверное тело, `413` — тело больше 32 КБ, `415` — неверный Content-Type, `502` — ошибка LLM. Тело ошибки: `{"status":"error","error":"…"}`.
- `/ask` сохраняется как совместимый адрес. Прототип локальный, без авторизации и хранения переписки.

Пример запроса из фронта, открытого на этом же сервере:

```javascript
const response = await fetch('/api/ask', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ question: 'Что такое кикер?' }),
});
const result = await response.json();
if (!response.ok) throw new Error(result.error);
console.log(result.answer, result.sources);
```

Ответ `200` (пример структуры, текст сокращён):

```json
{
  "status": "ok",
  "answer": "Кикер — дополнительная карта…",
  "sources": [{"id": "D01", "title": "Заголовок", "text": "Фрагмент корпуса…"}],
  "retrieved": [{"id": "D01", "score": 1.234}]
}
```

ID в примере условный. При отсутствии материала возвращается `200` со статусом `no_sources`, пояснением в `answer`, пустыми `sources` и выдачей в `retrieved`. Ссылки `sources` проверяются на принадлежность найденным фрагментам, но это не доказывает смысловую правильность ответа. Сервер не хранит сессии диалога; клиент может передать history и style (см. ниже). Потоковая генерация и CORS для другого origin не реализованы; для текущего фронта используйте общий адрес сервера. Ключ авторизации GigaChat в запрос браузера не добавляется.

## Продуктовый API (план)

## Доступ

- Все адреса `/api/*`, кроме регистрации и входа, требуют вошедшего пользователя (`REQ-002`). Без входа - ответ `401`, клиент переводит на страницу входа.
- Сессия - cookie `HttpOnly` после входа.
- Пользователь видит и меняет только свои раздачи (`R-011`); чужая раздача - `404`.

## Адреса

| Метод и адрес | Назначение | Требования |
|---|---|---|
| `POST /api/auth/register` | Регистрация | REQ-001 |
| `POST /api/auth/login` | Вход | REQ-001 |
| `POST /api/auth/logout` | Выход | REQ-002 |
| `GET /api/me`, `PATCH /api/me` | Профиль и настройка подсветки | REQ-023 |
| `GET /api/glossary/{term}` | Определение термина | REQ-023 |
| `GET /api/chats`, `POST /api/chats` | Список чатов, новый чат | REQ-003 |
| `GET /api/chats/{id}` | Название, переписка, список раздач с картами, улицей, банком и счётчиками, последняя выбранная раздача | REQ-003, REQ-004 |
| `PATCH /api/chats/{id}`, `DELETE /api/chats/{id}` | Переименовать чат, сохранить выбор раздачи или удалить весь чат | REQ-003 |
| `POST /api/chats/{id}/messages` | Текст, при наличии выбранная раздача; подтверждение начала отдельной раздачи | REQ-005, REQ-014, REQ-018 |
| `POST /api/chats/{id}/hands`, `PATCH /api/chats/{id}/hands/{hand}` | Решить введённую вручную ситуацию или исправить распознанную. Используется общий обработчик разбора | REQ-020 |
| `GET /api/chats/{id}/hands/{hand}` | Стол, сообщения, ходы по порядку и оценки пользователя | REQ-009, REQ-021, REQ-022 |
| `POST /api/chats/{id}/hands/{hand}/read` | Отметить просмотренные ответы до указанного сообщения | REQ-010 |

Сервер проверяет владельца чата и принадлежность раздачи чату для каждого запроса. Удаление отдельной раздачи не предусмотрено. При ответе передаются идентификаторы сообщения, чата и при наличии раздачи. Для явно другой ситуации статус `confirm_new_hand` предлагает создание новой раздачи. Клиент получает текст ответа по мере генерации для прокрутки согласно REQ-010.

## Вопрос и ответ

Запрос:
```json
{ "text": "Стеки по 100 ББ. Баттон поднял до 2.5 ББ, малый блайнд сбросил, у меня на большом блайнде туз-король разной масти. Что делать?" }
```

Ответ на теорию (`kind: theory`), например на "Что такое колл?":
```json
{
  "status": "ok",
  "kind": "theory",
  "answer": {
    "topic": "Колл",
    "explanation": "Колл - это когда вы доплачиваете ставку соперника и остаётесь в раздаче...",
    "example": "Соперник поставил 2 ББ, вы доплачиваете 2 ББ и смотрите следующую карту.",
    "tags": ["Чек", "Рейз", "Фолд"],
    "fragment_ids": ["glossary-call"]
  }
}
```

Ответ на раздачу (`kind: hand`):
```json
{
  "status": "ok",
  "kind": "hand",
  "answer": {
    "action": "3-бет", "size_bb": 13, "action_source": "exact",
    "tags": ["AKo - сильный бродвей", "BB против баттона", "Стек 100 ББ"],
    "explanation": "...",
    "fragment_ids": ["sol-pf-btn-open-bb", "concept-position"]
  },
  "situation": {
    "hero_cards": ["As", "Kd"], "hero_position": "BB",
    "villain_position": "BTN", "stack_bb": 100,
    "actions": [{"street": "preflop", "position": "BTN", "action": "рейз", "size_bb": 2.5},
                {"street": "preflop", "position": "SB", "action": "фолд"}],
    "board": [], "pot_bb": 4, "to_call_bb": 1.5
  },
  "math": { "pot_odds_pct": 27 }
}
```

`action_source` принимает значения `exact` и `nearest`. В обоих случаях действие берётся из сохранённого фрагмента-решения. Раздача хранит режим `analysis` или `training`. Оценка хода пользователя открывается сразу в разборе и после завершения в тренировке. До этого клиент получает нейтральную серую точку. Закрытые карты тренировочного соперника до вскрытия остаются на сервере.

Другие статусы:

| status | Когда | Что в ответе |
|---|---|---|
| `clarify` | Вопрос о раздаче, но не хватает данных (`REQ-011`) | `missing`: список недостающих полей, вопрос и общая префлоп-подсказка по известной руке |
| `no_sources` | Нет материала для ответа по теории (`REQ-012`) | Текст пояснения, без `action` |
| `off_topic` | Вопрос не о покере (`REQ-016`) | Текст отказа |
| `error` | Ошибка LLM (`REQ-013`), код ответа `502` | Текст ошибки; вопрос сохранён, можно повторить |

Общие вопросы новичка (REQ-025) используют тот же POST /api/ask и контракт ответа: вводные фрагменты передаются модели, источники возвращаются в sources, их ID — в retrieved. API дополнительных полей не требует.

## Контекст и стиль (REQ-026)

POST /api/ask дополнительно принимает history: до 12 объектов {role: user|assistant, content: строка до 1500 символов}, суммарно до 8000 символов. Текущий вопрос не дублируется в history. style: {prefix: короткая строка до 32 символов, verbosity: normal|brief|detailed, simple: boolean}; все поля необязательны, лишние поля отклоняются. Ограничение тела 32 КБ сохраняется; неверные поля дают 400.

Клиент отправляет только переписку выбранной раздачи либо общие сообщения чата; состояние карт/стола пока не передаётся. Ответ может включать style с эффективными настройками; фронтенд сохраняет их в текущем чате через sessionStorage. Чистая поддержанная просьба о стиле возвращает status=style_updated, answer=подтверждение, sources=[], retrieved=[]. Старое тело {question} работает как раньше. История служит контекстом, но не источником фактов.

Сервер передаёт проверенную историю в нативный messages GigaChat: system с правилами RAG, затем user/assistant истории, затем текущий user с вопросом, найденными документами и параметрами оформления. См. [официальную инструкцию](https://developers.sber.ru/docs/ru/gigachat/guides/keeping-context). X-Session-ID не используется для хранения истории.
