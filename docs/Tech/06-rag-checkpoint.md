# Контрольная точка по RAG

## Результат и границы этапа

Целевой прототип должен отвечать на вопросы по теории безлимитного Техасского Холдема на русском языке. Пользователь вводит вопрос, собственный BM25 находит документы, LLM отвечает по переданным фрагментам и указывает их ID. При нехватке сведений ответ сообщает об этом. Для демонстрации и повторяемого прогона достаточно локального запуска из командной строки. Интерфейс, аккаунты, PostgreSQL, симуляция соперника и рекомендации по раздачам относятся к продуктовой версии. Тестовые CSV PokerBench используются в отдельной проверке разбора раздач.

Результаты к сдаче по занятию 3, слайды 37–42, и методичке «НИРС», раздел 2: работающая цепочка RAG, корпус и benchmark с прогоном, README с командами запуска и проверки. Ниже зафиксирована спецификация до реализации. Шесть исходных Word-файлов лежат в рабочей папке проекта; выгрузка корпуса, индекс, вызов LLM и результаты будут созданы при реализации.

## Реализация и приёмка

1. Подготовить корпус и benchmark по таблицам. Проверить 30 уникальных ID документов, 15 уникальных ID вопросов и разрешимость всех ссылок на документы. Метаданные и эталоны вопросов используются для оценки. В поисковый индекс попадают только заголовки и тексты документов.
2. Реализовать инвертированный индекс самостоятельно. Для токена сохранить список документов и частоту, для документа — длину в токенах. Вычислять BM25 по частоте, нормировке длины и IDF `ln(1 + (N − df + 0,5)/(df + 0,5))`. Для старта взять `k1 = 1,2`, `b = 0,75`. Документы с равными баллами упорядочивать по ID. Передавать LLM только найденные фрагменты с положительной оценкой.
3. Применять одну предобработку к корпусу и запросам. Нормализовать регистр и варианты «ё/е». Сохранять целые обозначения `AhQd`, `AKs`, `OOP_RAISE_14`, `2.0bb`. При разборе составного обозначения также добавлять токены компонентов, например `oop`, `raise` и `14` для `OOP_RAISE_14`. Для совпадения русских запросов с английскими формами применять явные соответствия, например «рейз» ↔ `raise`, «колл» ↔ `call` и «ББ» ↔ `bb`. Начать с варианта без лемматизации, чтобы отдельно проверить вклад морфологии. Если сравниваем с лемматизацией, применять её к русским словам и сохранять специальные обозначения. В отчёте обосновать итоговый выбор.
4. Передать LLM вопрос и найденные фрагменты с ID. Вернуть ответ с ID использованных фрагментов или сообщить, что сведений недостаточно. При пустой выдаче сообщить об этом сразу. При непустой выдаче оценивать достаточность сведений по содержанию, поскольку совпадение слов само по себе не подтверждает ответ. Для подключения используется Groq через OpenAI-совместимый API с моделью `openai/gpt-oss-20b` (D-016).
5. Прогнать все 15 вопросов и сохранить по каждому ранжированный список документов с баллами, фрагменты, переданные модели, ответ, его ссылки и отметку сверки с эталоном. Зафиксировать конфигурацию, четыре метрики и краткий разбор ошибок. В README добавить фактические команды подготовки корпуса, запуска и прогона benchmark.

| Метрика | Как считать |
|---|---|
| Recall@k | Для каждого из 10 обычных вопросов доля релевантных документов, попавших в первые k. Затем среднее по вопросам. |
| MRR | Среднее обратных рангов первого релевантного документа на 10 обычных вопросах. Если релевантного документа нет на выбранной глубине, вклад равен нулю. |
| Accuracy | Число полностью правильных ответов по эталону, делённое на 10. |
| Correct Rejection Rate | Число корректных сообщений об отсутствии сведений без выдуманного ответа, делённое на 5. |

Для разработки используем `k = 5` и MRR по полной ранжированной выдаче. Параметры контрольного прогона фиксируются до запуска и согласуются по слайду 42.
