## Порядок работы

Сначала фиксируем поведение и способ проверки, потом описываем решение, делим на задачи и только затем меняем код.

1. Прочитай `STATUS.md` и нужные документы из `docs/Product/` и `docs/Tech/`.
2. Если меняется поведение - сначала обнови `docs/Product/` (требование REQ, сценарий GWT, правило R), потом `docs/Tech/`.
3. Внеси изменения в код.
4. Запусти проверки из `docs/Tech/05-verification.md`: тесты, а если менялись поиск или промпт - benchmark. Результат запиши в `docs/Service/verification.md`.
5. Добавь или дополни запись в `CHANGE_HISTORY.md` (см. "История изменений") и обнови `STATUS.md`.

Код, документы и результаты проверок должны соответствовать друг другу.

## Делай только то, о чём попросили

- Выполняй ровно поставленную задачу. Не добавляй функции, правки, документы, разделы и пометки, о которых не просили.
- Не придумывай задачи и открытые вопросы за команду. В `STATUS.md`, `docs/Service/decisions.md` и другие документы попадает только то, что команда обсудила и решила.
- Если заметил возможную проблему или улучшение - скажи об этом в ответе одной фразой и спроси. Не записывай это в документы и не делай сам без согласия.
- Не трактуй требования курса и пожелания шире, чем они сформулированы. Если не уверен, что имелось в виду, - спроси, а не додумывай.
- Не делай ничего, если сказали подождать.

## Изменил один документ - проверь связанные

| Изменил | Проверь |
|---|---|
| Требование в `03-requirements.md` | сценарии в `02`, экраны в `04`, проверки в `Tech/05-verification.md` |
| Экран или действие в `04` | требования в `03`, API в `Tech/04-api-and-access.md` |
| Правило в `05` | требования в `03`, данные в `Tech/03-data.md` |
| Архитектуру или API в `Tech/` | `WORKSPACE_MAP.md`, `02-running.md` |
| Состав документов | `docs/README.md`, `docs/document-manifest.json` |

## Нумерация

- Требования: `REQ-001`, `REQ-002`, ... Сценарии проверки: `GWT-001`, ... Правила: `R-001`, ... Решения: `D-001`, ... Открытые вопросы: `Q-001`, ...
- Номера не переиспользуются. Если пункт отменён, он остаётся с пометкой "отменено".
- Записи в `CHANGE_HISTORY.md`: `CH-ГГГГ-ММ-ДД-NNN`.

## История изменений

- Одна запись в `CHANGE_HISTORY.md` = один набор изменений, который уходит в git (один Pull Request). Промежуточные правки в процессе работы отдельными записями не оформляются.
- Перед добавлением записи проверь, что уже отправлено: `git log origin/main --oneline` и `git status`. Если верхняя запись описывает изменения, которые ещё не запушены, - дополни её, а не создавай новую.
- Новая запись создаётся только для изменений, которые идут после последнего запушенного набора.
- Если до отправки изменения отменены или переделаны, запись описывает итоговое состояние, а не историю промежуточных вариантов.

## Существенные новые функции

Для крупной новой функции создаётся папка `docs/Update/UPD-NNN-краткое-название/` с описанием предлагаемого изменения. После проверки изменения переносятся в `docs/Product/` и `docs/Tech/`, а пакет уходит в `docs/Archive/Updates/`.

## Git

- `main` - всегда рабочая версия. Напрямую в `main` не пушим.
- Одна задача - одна ветка: `rag/...`, `infra/...`, `ui/...`, `docs/...`.
- Перед началом задачи: `git checkout main`, `git pull`, `git checkout -b <ветка>`.
- Изменения попадают в `main` через Pull Request после просмотра хотя бы одним участником.
- Коммиты маленькие, с понятным описанием на русском.

## Ограничения

- Ключи API и `.env` не коммитим.
- В корпус не кладём платные книги и курсы. Только материалы с открытой лицензией или собственные конспекты; источник и лицензия каждого документа указываются (см. `docs/Product/05-rules-and-data-meaning.md`).
- Математику покера (шансы банка, ауты) считает код, а не LLM.
