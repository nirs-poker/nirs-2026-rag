# Benchmark КТ2

В наборе 30 [разделов](../../server/corpus/documents.jsonl) из шести Word-файлов, 10 обычных вопросов с эталонами и 5 ловушек. У обычного вопроса есть не менее трёх релевантных ID. Разметка перенесена из [спецификации КТ2](../../../docs/Tech/06-rag-checkpoint.md). Вопросы и примечания об источниках в индекс не входят.

Чтобы проверить чат вручную, используйте [инструкцию запуска](../../../README.md#как-запустить-чат-бота). Команды benchmark выполняются из корня проекта.

Для генерации используется Groq `openai/gpt-oss-20b`. Benchmark читает ключ из окружения процесса, но не загружает `.env` автоматически: сначала выполните шаг загрузки переменных из [инструкции запуска](../../../docs/Tech/02-running.md#cli-и-benchmark). `--search-only` не требует ключа. Сквозной прогон отправляет вопросы и найденные фрагменты в Groq.

```powershell
python -X utf8 code/tests/benchmark/run.py --search-only --output code/tests/benchmark/results/search.json
python -X utf8 code/tests/benchmark/run.py
```

Первая команда проверяет индекс. Вторая требует настроенного API LLM и сохраняет результат каждого вопроса в `results/local.json`. В отчёте есть конфигурация, хеши корпуса и вопросов, ранжирование с баллами, переданный модели контекст, ответы и ссылки. Ошибка модели отмечается как `error` и завершает команду с ненулевым кодом. Ошибка не засчитывается как корректный отказ.

Retrieval использует BM25 с `k1=1.2`, `b=0.75`. Документы и запросы проходят одинаковую обработку. Нижний регистр и замена «ё» на «е» убирают различия в написании. Короткий список стоп-слов снижает вклад служебной лексики. Полная лемматизация не нужна для этой версии: небольшой словарь сводит распространённые покерные словоформы и русские и английские обозначения. Коды карт сохраняются целиком, к составным обозначениям добавляются их части, чтобы работали точные и частичные совпадения.

Recall и контекст модели используют первые пять документов. По умолчанию MRR считается по полной выдаче. Для другой конфигурации передайте `--k` и `--mrr-depth`.

| Метрика | Что считаем |
|---|---|
| Recall@5 | Средняя доля релевантных документов в первых 5 результатах по 10 обычным вопросам. |
| MRR | Среднее обратное место первого релевантного документа по тем же 10 вопросам. Если такого документа нет на выбранной глубине, вклад равен 0. |
| Accuracy | Доля полностью правильных ответов на 10 обычных вопросов. Сверяем смысл с эталоном и проверяем, что источники поддерживают факты. |
| Correct Rejection Rate | Доля из пяти ловушек, которым система вернула отказ `no_sources`. |

Сверьте десять ответов с эталонами вручную. Оценка «верно» требует всех ключевых фактов, отсутствия противоречий и опоры на перечисленные источники. Перефразирование допускается. Для десяти обычных вопросов создайте файл JSON вида `{"Q01":{"answer":"точный ответ из отчёта","correct":true,"note":"обоснование"}}` со всеми ID от Q01 до Q10. Затем добавьте оценки и две итоговые метрики в отчёт:

```powershell
python -X utf8 code/tests/benchmark/run.py --grades grades.json
```

Программа проверяет, что оценки относятся к ответам текущего прогона, и вычисляет долю корректных отказов по статусам ловушек.

## Результат поиска

В [прогоне поиска](results/search.json) Recall@5 = **0,8417**, MRR = **1,0000**. Первый результат релевантен для каждого обычного вопроса. Пять фрагментов остались за пределами первой пятёрки: D28 в Q03, D10 в Q04, D06 в Q05, D01 в Q06 и D23 в Q10. В составных вопросах отдельные части контекста могут проигрывать документам, которые совпадают по большему числу слов.

[Полный прогон Groq](results/groq-kt2.json) дал Accuracy 4/10 и Correct Rejection Rate 5/5. В Q01 и Q06 модель ошиблась в выводе даже при наличии прямого ответа в контексте. В Q03 ответ верен по смыслу, но ссылка подтверждает только часть ответа. В Q04 нарушена нотация PokerBench, в Q05 неверно описано распределение фишек после фолда, в Q09 смешаны потенциальные и обратные потенциальные шансы.

После ограничения API продолжайте текущий прогон командой `python -X utf8 code/tests/benchmark/run.py --resume`. Скрипт пропустит уже завершённые вопросы.

## Groq: исходный уровень, 2026-11-20

Повторяемый эксперимент с другим системным промптом запускается отдельной командой. `.env` загружается автоматически; рабочий `rag.py` не меняется:

```bash
python -X utf8 code/tests/benchmark/compare_prompt.py --baseline code/tests/benchmark/results/2026-11-20-groq-baseline-resumed.json --output code/tests/benchmark/results/prompt-comparison.json
```

Выходной файл должен быть новым. Скрипт использует сохранённые вопросы и фрагменты `context`, проверяет совпадение модели, сохраняет оба промпта, SHA256 baseline и ошибки попыток. Эталоны не передаются модели. Между вопросами пауза 15 секунд (`--delay`), при ошибке — до двух повторов с паузами 30 секунд. Для оценивания используется тот же `run.py --output … --grades …` и тот же критерий, что для baseline. Конфигурация generation в отчёте отражает текущие фиксированные параметры клиента; при изменении клиента эксперимент необходимо пересмотреть.

Для сравнения моделей передайте явный `--model openai/gpt-oss-20b` или `--model openai/gpt-oss-120b` с тем же `--baseline` и разными новыми `--output`. Это отключает только требование совпадения модели с историческим baseline; промпт v2 и фиксированный контекст сохраняются. Явный ID имеет приоритет над `LLM_MODEL` только внутри эксперимента, `.env` и рабочий клиент не изменяются.

Проведён сквозной прогон `openai/gpt-oss-20b`: temperature=0, reasoning_effort=low, max_tokens=700, строгая JSON Schema, BM25 k1=1.2/b=0.75, k=5, MRR по полной выдаче. Промпт, корпус и поиск не изменялись. Исходный код — коммит `37d2b33`.

| Метрика | Результат |
|---|---|
| Recall@5 | 0,8417 |
| MRR | 1,0000 |
| Accuracy по строгому критерию | 0,30 (3/10) |
| Correct Rejection Rate | 1,00 (5/5) |

Это один небольшой прогон, а не устойчивая оценка качества. Оценки выполнены агентом по эталонам и текстам источников, без отдельной проверки участником команды. Полностью правильными считаются Q02, Q07, Q08; краткий Q08 принят, поскольку отвечает на запрошенную долю и подтверждён D19. Для Q03, Q09 и Q10 основной смысл верен, но строгую проверку нарушают неполные ссылки или лишние неподтверждённые/ошибочные утверждения. Причины каждой оценки сохранены в JSON.

Первый проход получил 6 ответов `ok`, 2 отказа `no_sources` и 7 ошибок HTTP 429. Ошибки API не засчитывались как отказы. Повторены только неуспешные запросы с паузами 15 секунд; Q10 дополнительно вернул HTTP 400, затем прошёл с теми же параметрами. Успешные ответы первого прохода сохранены. Итоговые метрики относятся к собранному прогону после повторов, а не к надёжности одного прохода.

|---|---|---|

| Q04 | RAISE_5 вместо префлоп-записи 5.0bb | Перепутаны два формата из D30 |
| Q05 | Неточная формулировка о взносе в основной банк после фолда | Обобщение сверх перечисленных источников |
| Q06 | Победителем названа QJ вместо A3 | Прямое противоречие D14 и собственной фразе о кикере |
| Q09 | Добавлен термин direct implied odds | Неверное дополнение, отсутствующее в корпусе |
| Q10 | Добавлены блокеры без подтверждения указанными источниками | Правильный расчёт дополнен неподтверждённым объяснением |

Главное наблюдение: высокий MRR не гарантирует верный ответ. Для Q01, Q04 и Q06 достаточный контекст уже найден, поэтому одной настройки BM25 недостаточно. Следующий предмет сравнения — точность переноса фактов и полнота ссылок при другом промпте или модели на фиксированной выдаче. Изменений промпта или модели по результатам этого прогона пока не внесено.

## Сравнение промптов, 2026-11-20

Кандидат `CANDIDATE` из `compare_prompt.py` проверен на точно тех же вопросах и упорядоченных фрагментах исходного прогона. Модель, JSON Schema и параметры генерации сохранены. Инструкция требует отдельно проверять утверждения, сохранять формат обозначений и указывать подтверждающие источники для каждого факта; эталонные ответы в запрос не передаются. Рабочий `SYSTEM` в `code/server/rag.py` не изменён.

| Метрика | Исходный промпт | Кандидат v2 |
|---|---|---|
| Recall@5 | 0,8417 | 0,8417 (та же выдача) |
| MRR | 1,0000 | 1,0000 (та же выдача) |
| Строгая Accuracy | 3/10 (0,30) | 6/10 (0,60) |
| Correct Rejection Rate | 5/5 | 5/5 |

Исправились Q01 (порядок хода), Q03 (полнота ссылок), Q09 (удалён неверный английский термин). Правильными остаются Q02, Q07, Q08. Q04 по-прежнему смешивает префлоп- и постфлоп-записи; Q05 содержит ошибки побочного банка и фолда; Q06 утверждает, что дама выше туза; Q10 добавляет блокеры без подтверждения перечисленными источниками. В Q05 формулировка стала хуже, хотя бинарная оценка осталась «неверно».

Все 15 запросов завершены; Q09 потребовал одного повтора после HTTP 429. Один вопрос-ловушка с пустым контекстом отклоняется кодом без LLM в обоих вариантах. Оценка выполнена агентом по тому же строгому критерию; это не независимая человеческая проверка. Для Q01 принято однозначное описание «игрок после BB» вместо аббревиатуры UTG, для Q08 — краткий верный порог 25%, как и в baseline.

- [Результат v2: вопросы, контексты, оба промпта и оценки](results/2026-11-20-groq-prompt-v2.json).
- [Оценки v2 с объяснениями](results/2026-11-20-groq-prompt-v2-grades.json).

Рост на 30 процентных пунктов относится к известному набору из 10 обычных вопросов, использованному при подготовке инструкции. Сравнение выполнено с историческим baseline, а не одновременным контрольным прогоном; недетерминизм/изменения API не исключены. Рост не доказывает обобщение на новые вопросы. Кандидат оставлен экспериментальным: критические ошибки фактов сохраняются, рабочий промпт не заменён.

## Сравнение GPT-OSS 20B и 120B, 2026-11-20

Обе модели прогнаны заново в одном временном окне с промптом-кандидатом v2. Программно подтверждено совпадение системного промпта, всех 15 вопросов, порядка и текста фрагментов, SHA256 исходного baseline и параметров генерации (temperature=0, reasoning_effort=low, max_tokens=700, строгая JSON Schema). Изменяется только ID модели. Возможность использовать одинаковую схему и low effort подтверждается [Structured Outputs Groq](https://console.groq.com/docs/structured-outputs) и [Reasoning Groq](https://console.groq.com/docs/reasoning).

Оба прогона завершились без ошибок API и повторных попыток. Вопрос Q11 с пустой выдачей отклонён кодом без вызова LLM в обоих случаях. Recall@5=0,8417 и MRR=1,0000 унаследованы от фиксированного поиска, а не измеряют работу моделей.

| Метрика | gpt-oss-20b | gpt-oss-120b |
|---|---|---|
| Строгая Accuracy | 7/10 (0,70) | 7/10 (0,70) |
| Correct Rejection Rate | 5/5 | 5/5 |
| Неверные обычные ответы | Q04, Q05, Q06 | Q04, Q05, Q09 |
| Ошибки API | 0 | 0 |

| Вопрос | 20B | 120B |
|---|---|---|
| Q04, запись префлопа | Неверный формат, включая OOP_RAISE_5 | Неверный формат raise 5bb вместо 5.0bb |
| Q05, побочный банк и фолд | Ошибочное описание взносов и сохранения фишек | Ошибочно утверждается, что фишки сбросившего только в основном банке |
| Q06, сравнение кикеров | Ошибочно выигрывает дама | Верно выигрывает туз |
| Q09, виды шансов | Все три вида объяснены верно | Прямые шансы ошибочно названы implied odds |

Новый 20B дал 7/10 вместо прежних 6/10 с тем же промптом v2: в Q10 исчезло неподтверждённое дополнение о блокерах. Даже при temperature=0 ответы могут отличаться; один прогон недостаточен для доказательства устойчивого преимущества. Оценки выставлены агентом по тому же строгому критерию, независимой проверки участником команды не было. На этом небольшом известном наборе преимущества 120B по общей Accuracy не обнаружено; это не доказывает равенство моделей на других вопросах. Задержка, фактическое число токенов и стоимость не измерялись. Рабочая модель и промпт не изменены.
